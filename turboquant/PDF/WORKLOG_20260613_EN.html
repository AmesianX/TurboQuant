Why the t/s Jitters 23 → 16 → 19

t/s = (tokens accepted per MTP round) / (round time). Round time ≈ constant (~25ms, target verify GPU pass); tokens-per-round swing 1→3 with the acceptance rate (96-100%).
  • Acceptance variance (dominant) — predictable spans (lists, common phrasing) accept↑ → ~20 t/s; novel content (numbers, names) → ~16. Sentence-to-sentence swing = the nature of speculative decoding, not a bug.
  • Context-growth drift — KV grows → round time creeps up. Step-jump at 256-multiple boundaries.
  • Metric conflation — 23 (peak) / 16 (essay aggregate, incl. prompt-eval) / 19 (recent window) have different denominators.

Key Lessons

  • Measure before implementing — pre-empted the high-risk #2 change with data. Blocked the "touched it but it didn't go up" trap.
  • Graph build overlaps async GPU = off critical path — CPU-side optimizations (#1-#5) can't lift a GPU-bound decode.
  • Topology change ≠ bit-identical — a padded view changes fp-accumulation order. Even "math unchanged" makes bit-identity too strict → judge by perplexity.
  • CI hygiene: all-stop → run the final build fresh — never preserve in-flight builds. Prevents zombies / queue pollution.
  • merge -s ours — a superior fork reconciles upstream divergence with 0 lines. Only real merges need the workflow-restore.
  • Memory-bound → only quant/expert count is a lever — matmul 52% is the LPDDR wall; kernel fusion saves launch overhead only.
