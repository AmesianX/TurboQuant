# Fix: Reduce Vulkan graph nodes from 407,880 to ~6,239 (bs=512)

## Root Cause

Two factors contribute to `graph nodes = 407880 (with bs=512), 259 splits`:

### 1. `DSV4_HC_WEIGHTED_SUM` missing from Vulkan (Primary — 259 splits)

`DSV4_HC_WEIGHTED_SUM` is called **2× per layer** (attention pre-mix + FFN pre-mix) + 1× for the output head. With ~150 layers, that's ~300 ops falling back to CPU, creating 259 scheduler split boundaries. Each split boundary inflates graph allocation by `GGML_SCHED_MAX_SPLIT_INPUTS * 2 * n_copies = 256 * 2 * 4 = 2,048` reserved slots.

**Impact**: 259 splits × 2,048 ≈ 530,368 reserved slots (allocation, not actual nodes)

### 2. Actual computation graph size for bs=512 (Secondary)

The actual `ggml_graph_n_nodes(gf)` for bs=512 is 407,880 vs 6,239 for bs=1. This is ~65× growth for 512× batch. Likely causes:
- Flash Attention with bs=512 may create per-token graph nodes instead of a single fused kernel
- Other ops scaling poorly with batch size in graph representation

## Plan

### Step 1: Implement DSV4_HC_WEIGHTED_SUM for Vulkan (Recommended — eliminates 259 splits)

Following the existing `DSV4_HC_EXPAND` pattern (4 src tensors, F32-only):

**New file**: `ggml/src/ggml-vulkan/vulkan-shaders/dsv4_hc_weighted_sum.comp`
- GLSL shader: element-parallel kernel, each thread computes one `[n_embd, n_tokens]` output element
- Computes: `dst[d, t] = sum_hc(x[d, hc, t] * weights[hc, t])`
- Workgroup: `{256, 1, 1}`, grid = `ceil(n_embd * n_tokens / 256)`
- Push constants: `n_embd`, `n_hc`, `n_tokens`, stride params for x/weights/dst

**Modified**: `ggml/src/ggml-vulkan/ggml-vulkan.cpp`
- Add `ggml_vk_push_constants_dsv4_hc_weighted_sum` struct
- Add `pipeline_dsv4_hc_weighted_sum_f32` member to `ggml_vk_device`
- Pipeline creation in `ggml_vk_device_init`
- Case in `ggml_vk_select_pipeline`
- Case in `ggml_vk_build_graph` (graph dispatch)
- Case in `ggml_backend_vk_device_supports_op`
- Case in offload checks

**Modified**: `ggml/src/ggml-vulkan/vulkan-shaders/vulkan-shaders-gen.cpp`
- Register `dsv4_hc_weighted_sum.comp`

### Step 2: Investigate bs=512 graph node inflation (if Step 1 doesn't reduce enough)

After Step 1, if actual computation nodes (not split overhead) are still ~400k:
- Profile `graph_reserve` to identify which op types create the most nodes at bs=512
- Likely candidate: Flash Attention graph construction creates per-token nodes instead of fused kernel calls
- Fix would be in the Flash Attention graph builder to emit a single fused node for batched attention

## Expected Results After Step 1

| Metric | Before | After Step 1 |
|--------|--------|---------------|
| `graph splits` (bs=512) | 259 | ~0-5 (only ops without GPU impl) |
| `graph splits` (bs=1) | 177 | ~0-3 |
| `Vulkan_Host compute buffer` | 11,346 MiB | ~0 MiB |
| `graph nodes` (bs=512) | 407,880 | Depends on Step 2 |

Note: The 407,880 figure reported is `ggml_graph_n_nodes(gf)` (actual computation nodes), NOT the `graph_size` allocation formula. Step 1 eliminates splits, but the actual computation node count depends on how the model graph is constructed for bs=512. If the model graph itself creates per-token nodes for bs=512, that's a separate graph construction issue.
