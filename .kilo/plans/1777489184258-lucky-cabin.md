# Plan: Fix DSV4 Vulkan Null Pipeline Crash

## Diagnosis

All 5 DSV4 pipelines are fully registered in the chain:
- Shader `.comp` files exist
- `vulkan-shaders-gen.cpp` registers all 5
- `ggml-vulkan.cpp` declares, inits, selects, and dispatches correctly
- Build artifacts (`ggml-vulkan-shaders.hpp`) declare all 5 `*_len` externs

**Root cause**: `GGML_ASSERT(pipeline != nullptr)` in the dispatch functions aborts if the pipeline is null, but provides no diagnostic info about WHICH pipeline failed. In Release builds, this manifests as a crash with null pointer at 0x0.

Additionally, `ggml_vk_op_get_pipeline` for `DSV4_HC_EXPAND` (line 9827) checks only `src0`, `src1`, `src2`, `dst` but NOT `src3` (comb). The `ggml_backend_vk_device_supports_op` (line 16200) correctly checks all 4.

**Riga 757:** `256 → 64` (già fatto, non toccare)

## Note

- Le null guard con `GGML_LOG_ERROR` + `return` sono preferibili a `GGML_ASSERT` perché:
  1. Forniscono il nome della pipeline nulla nel log
  2. Non abortono il processo (permettono il fallback al backend CPU se il scheduler lo supporta)
  3. Funzionano sia in Debug che in Release
- Lo `src3` check nel pipeline selector allinea `ggml_vk_op_get_pipeline` con `ggml_backend_vk_device_supports_op`
- I contatori sono diagnostici e possono essere rimossi dopo il debugging
